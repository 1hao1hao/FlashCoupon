# 验证报告

执行日期：2026-11-09（Asia/Shanghai）。工作区：`D:\backend`。

## 环境与复现

- Docker Desktop Linux Engine，28 个逻辑 CPU，约 15.5 GiB 内存；同一 Engine 还有现存演示服务，未停止其他项目容器。
- Go 1.24 容器工具链；MySQL 8.0.41、Redis 7、RocketMQ 5.3.1、ShardingSphere-Proxy 5.5.2、k6 0.57.0。
- 实际测试开启 `compose.sharding.yaml`，用户券和商户模板投影均经过 Proxy 写入真实物理分片。
- 命令：`./scripts/verify.ps1 -Benchmark -Faults`；输出见 `reports/verify.log`。最终源码补充初始化保护后的 race/vet 复查见 `reports/final-integration.log`。

所有指标来自本地实测；不是生产容量承诺。已有历史测试数据、后台对账和其他容器会影响结果。此轮为功能与性能对比验收，没有以多轮置信区间确定最大稳定吞吐。

## 业务与可靠性验收

| 场景 | 结果 |
|---|---|
| 200 并发请求，库存 30，含同用户同请求重放 | 唯一受理 30，最终发出 30，唯一用户 30 |
| 将已受理消息重新写 Stream，多次直接重放消费者 | 发券数和数据库库存不变 |
| 同步发券相同请求重复提交 | 同一张券，不重复扣库存 |
| 同一券/订单并发核销 20 次 | 全部返回幂等成功，仅一个核销结果 |
| 已核销券换订单；同一订单换另一张券 | 拒绝，条件更新和订单唯一约束生效 |
| 门槛、商户归属、到期时间、券状态过滤 | 单元测试及集成测试通过 |
| xlsx 4 个数据行含重复用户 | 唯一 3 人，受理 3，最终发券 3 |
| 永久 SQL 拒绝，重复执行补偿 3 次 | Redis 库存只回补一次，限领恢复为 0 |
| 券过期、用户缓存清空重建 | 过期流转生效，不可核销、不参与优惠报价 |
| Redis 活动库存键丢失 | 抢券和盲目重新预热均被拒绝 |
| SQL 已提交、用户投影未写入 | 对账补齐唯一用户券 |
| Redis 库存/限领计数漂移 | CAS 对账修复；暂停/恢复活动测试通过 |
| 用户 ID `9007199254740993`（超过 2^53） | Lua 保留完整 int64 身份，发券用户正确 |
| Go race / go vet | 通过；没有保留已知竞态失败 |
| 两库四表 SQL 审计 | 四张用户券分表和四张商户模板分表均有真实数据；超发与限领违规计数均为 0 |

过程中发现并修复了 MQ 卷权限、Topic 启动顺序、NameServer DNS 适配、Gin Context 被 SQL 后台 goroutine 复用导致的竞态，以及 Lua cjson 大整数舍入问题。

## k6 结果

| 场景 | 请求 / VU / 库存 | HTTP 受理 QPS | 最终发券 TPS | 抢券 P95 (ms) | 抢券 P99 (ms) | 最终唯一发券 |
|---|---|---:|---:|---:|---:|---:|
| MySQL 同步直发 | 500 / 30 / 500 | 63.47 | 62.00 | 1328.31 | 1457.50 | 500 |
| Redis 异步链路 | 500 / 30 / 500 | 974.66 | 66.41 | 71.39 | 79.46 | 500 |
| 相同请求重复提交 | 500 / 30 / 500，10 个唯一用户 | 390.93 | 6.48 | 314.12 | 403.16 | 10 |
| 库存竞争 | 2000 / 100 / 1000 | 1416.43 | 50.59 | 50.98 | 82.71 | 1000 |

对应原始数据：`reports/direct.json`、`async.json`、`async-duplicate.json`、`async-contention.json`。所有 k6 业务检查和库存断言通过。库存竞争中 1000 次成功受理、1000 次库存不足业务拒绝，最终无超发。该行延迟包含拒绝响应，不与全部成功请求的延迟直接等价比较。

受理 QPS 使用成功 HTTP 受理数量除以抢券请求窗口；重复请求会多次返回同一事件，因而该行 QPS 不是唯一发券速度。最终 TPS 使用唯一发券数除以从开抢到排空的总时间。k6 内置 Counter 的 `rate` 会覆盖 teardown 等待期，因此报告使用自定义 `measurements.accepted_http_qps`。

异步方案改善了请求响应和削峰，但最终落库吞吐仍受模板行锁、MySQL 事实事务、用户分片写入和后台对账影响；本次实测没有显示最终 TPS 随受理 QPS 等比例增长。

批量压测用 Excelize StreamWriter 生成 100 人名单，经 HTTP multipart 导入、批量 Stream、抢券 Stream、RocketMQ、Worker，最终发券 100 张，pending 为 0，库存一致。输出在 `reports/verify.log` 的 batch.js 段。

## 真实故障恢复

脚本：`scripts/recovery.ps1`。最后一轮结果保存在 `reports/recovery.json`：

1. 停止 RocketMQ Broker，保持 API 与 Redis 运行。
2. 受理 20 个唯一请求：SQL 已发 0，Redis 剩余 0，pending 20。
3. 观察到 Stream PEL 中 1 条待确认记录，其他记录尚未被取出。
4. 停止应用，重启 Redis（恢复 AOF），恢复 Broker 和应用。
5. 约 13.85 秒观测到收敛；整个故障编排约 37.17 秒。
6. 最终 SQL 成功事实 20、用户券投影 20、DB/Redis 剩余均为 0、pending 0、对账一致。

该结果覆盖消息中继 pending 恢复、未读取 Outbox 恢复、应用重启和 Redis 持久化重启。没有模拟磁盘损毁、跨机器故障或多主切换；这些不在单机 Compose 的保障范围内。
